# Codex CLI 无状态服务需求设计

## 1. 背景

当前 Codex CLI 同时承担交互入口、会话生命周期管理、本地状态读写、工具执行编排和用户界面输出等职责。该模型适合单用户、本地终端、长生命周期会话场景，但在服务化场景下存在以下限制：

- 进程内会话状态与请求处理耦合，水平扩展能力受限。
- 会话恢复、工具调用、审批状态、执行环境状态之间边界不清晰。
- CLI 作为长生命周期交互进程时，调用方难以用标准服务治理能力管理超时、重试、隔离和观测。
- 不同前端接入方式需要复用 Codex 能力时，容易重复实现会话调度、输出流转和错误处理逻辑。

目标部署场景为云端几十到上百个 Codex 服务实例。客户端不保持与同一 Codex 实例的长期会话连接；每次用户输入被建模为一次独立请求。任意服务实例在收到后续请求时，都必须能基于云端持久化状态恢复线程上下文并执行下一次 turn。

本需求设计的目标是定义一个将 Codex CLI 改造为无状态服务的产品与系统需求边界。本文不定义最终内部模块拆分方案，也不替代后续架构设计文档。

## 2. 目标

### 2.1 总体目标

将 Codex CLI 从以本地交互进程为中心的形态，改造成可由外部客户端按请求调用的无状态服务入口。服务实例不依赖进程内长期会话状态完成请求处理；请求所需上下文必须由请求参数、外部持久化存储或可重建资源提供。

### 2.2 具体目标

- 支持外部客户端通过稳定协议提交单次对话请求、查询请求状态、流式读取结果、取消运行中请求。
- 服务实例可被横向扩展；任一兼容实例可处理同一逻辑会话的后续单次请求。
- 长链接对话模型改造为单次对话模型；每次请求结束后，服务实例不得依赖进程内 `CodexThread` 保留后续请求所需状态。
- 任意节点必须能基于线程标识、请求输入和云端持久化状态 resume 并执行下一次 turn。
- 进程重启后，可通过云端持久化状态恢复可恢复任务，或以明确错误返回不可恢复任务。
- CLI 仍保留本地命令入口，但本地命令应作为服务客户端或服务兼容入口，而非唯一执行主体。
- 状态写入必须显式分类，避免将临时运行状态隐式绑定到进程生命周期。
- Skill 定义从集中式 NFS 读取，并在服务实例本地缓存；缓存必须具备版本识别和失效机制。

## 3. 非目标

- 不要求移除 Codex 的所有持久化数据。无状态服务表示服务进程不持有不可替代的业务状态，不表示系统不使用云端数据库、文件存储、对象存储或 NFS。
- 不要求首个版本提供多租户 SaaS 能力。
- 不要求首个版本重写模型调用、工具执行、沙箱、审批和 MCP 能力。
- 不要求改变现有 Codex CLI 的全部用户命令语义；兼容性按迁移阶段定义。
- 不要求将所有交互式 TUI 能力完整映射为远程服务能力。
- 不要求首个版本实现跨地域 Skill 分发；NFS 可作为单区域共享源。
- 不要求运行中任务跨实例接管。运行中任务可以绑定到创建或调度它的服务实例。
- 不要求审批流程脱离原始连接或原始运行实例。审批可继续由活动连接和进程内 listener 驱动。
- 不要求 PTY、shell session、MCP 会话跨实例恢复。实例失效时，相关临时运行状态可中断或失败。
- 不要求在两次用户输入之间保留同一进程内的活动线程对象。后续输入必须通过云端状态重建上下文。

## 4. 状态分类

### 4.1 请求状态

请求状态指完成一次 API 调用必须携带的输入，包括用户输入、模型参数、工作目录、权限配置、工具策略、目标线程或请求标识。请求状态不得只存在于服务进程内存中。

### 4.2 可持久化业务状态

可持久化业务状态包括线程、turn、消息项、工具调用记录、审批记录、请求状态、审计日志、用户配置快照。该状态应由云端持久化层管理，并通过显式标识读取。

云端持久化层至少需要满足以下要求：

- 服务实例不得将本地文件系统作为业务状态的唯一持久化介质。
- 线程、单次请求、turn、事件、配置快照和现有 state_db 承载的元数据应使用云端数据库或等价强一致持久化组件。
- 大体积事件载荷、执行产物和日志归档可使用对象存储，但元数据必须可通过请求、turn 或线程标识索引。
- 所有状态写入必须具备租户、调用方、线程、turn 和请求关联字段。
- 本地磁盘只允许作为临时缓存、执行工作区或可重建数据目录。

### 4.3 临时运行状态

临时运行状态包括正在执行的子进程句柄、流式输出缓冲、正在连接的 MCP 会话、活动沙箱、后台 PTY。该状态可在单个服务实例内存在，但必须具备明确的失效语义：

- 可恢复：通过持久化请求记录和幂等重放恢复。
- 不可恢复：实例失效后请求进入失败或中断状态，并暴露可诊断原因。

### 4.4 禁止隐式依赖的状态

以下状态不得作为跨请求正确性的唯一来源：

- 进程内线程映射。
- 进程内最近一次配置解析结果。
- 进程内审批缓存。
- 进程内工具目录或 MCP 工具列表缓存。
- 进程内或本地磁盘中的 Skill 缓存。
- 终端 UI 内部状态。

## 5. 用户与调用方

### 5.1 本地 CLI 用户

本地用户继续通过 `codex` 命令使用能力。改造后，本地 CLI 可以启动内嵌服务，也可以连接已有服务。用户不应感知不必要的协议细节。

### 5.2 IDE 或桌面客户端

IDE、桌面客户端需要稳定的服务协议、流式事件、取消能力、请求恢复能力和结构化错误。

### 5.3 自动化系统

CI、批处理系统、远程执行系统需要非交互调用、幂等请求、机器可解析输出、超时控制和资源限制。

## 6. 核心场景

### 6.1 单次对话请求

调用方每次提交一个用户输入请求。请求必须包含：

- 线程标识，或创建新线程的声明。
- 输入内容。
- 工作目录或远程工作区引用。
- 模型与推理配置。
- 权限与审批策略。
- 可选的额外上下文引用或显式上下文内容。
- 幂等键。

服务实例收到请求后，必须先从云端状态读取线程历史、线程元数据、配置快照、state_db 元数据和 Skill 版本信息，再构造本次 turn 的运行上下文。服务返回本次请求或 turn 标识，并开始产生结构化事件。

### 6.2 任意节点 resume

同一线程的第 N 次请求完成后，第 N+1 次请求可以命中任意服务实例。新实例必须能通过线程标识从云端状态恢复：

- 已持久化的线程历史。
- 上次 turn 完成后的线程元数据。
- state_db 云端元数据。
- 上次有效配置快照或可重建配置输入。
- 本线程最近一次绑定的 Skill 指纹集合。

恢复后的模型上下文必须与同一实例连续处理时等价。不得依赖前一次请求所在实例的进程内 `CodexThread`、context manager、thread map 或本地状态缓存。

### 6.3 查询请求状态

调用方可通过请求或 turn 标识查询当前状态。状态至少包括：

- `queued`
- `running`
- `requires_approval`
- `completed`
- `failed`
- `cancelled`
- `interrupted`
- `expired`

### 6.4 流式读取请求结果

调用方可订阅本次请求事件流。事件必须可排序、可分页或可从指定游标继续读取。客户端断线重连后不得依赖原服务实例保留内存缓冲。

### 6.5 取消运行中请求

调用方可提交取消请求。取消请求必须是幂等操作。服务应尽力终止运行中工具、子进程和模型请求，并将最终状态写入持久化层。

### 6.6 处理审批

当运行中请求需要审批时，服务应产生审批请求事件。审批流程允许继续依赖活动连接和运行实例。审批结果应被记录到云端状态，用于审计和请求历史追溯，但首个版本不要求审批请求成为可被任意实例解析的独立资源。

### 6.7 恢复事件流

调用方可从上次确认的事件游标继续读取事件。服务必须能够从持久化事件记录或可重建事件源恢复输出。

## 7. 功能需求

### 7.1 服务协议

- 必须提供稳定的请求-响应接口。
- 必须支持流式事件输出。
- 必须为每个请求提供结构化错误码。
- 必须支持幂等键，避免客户端重试导致重复请求。
- 必须暴露服务版本、协议版本和能力列表。

### 7.2 请求模型

- 每个单次请求必须有全局唯一标识。
- 每个单次请求必须绑定线程标识；线程标识是跨节点 resume 的主要业务键。
- 每个单次请求必须记录创建时间、更新时间、最终状态、调用方标识和输入摘要。
- 请求状态转换必须具备单调性；已终结状态不得回到运行态。
- 运行中请求必须具备超时或租约机制。
- 同一线程同一时刻是否允许多个运行中请求并发执行必须由协议显式定义；默认应串行化同一线程的 turn。

### 7.3 上下文模型

- 请求必须显式声明上下文来源。
- 会话历史、用户指令、项目指令、配置快照必须具备可追踪来源。
- 单个上下文片段必须具备大小上限。
- 不得将未设上限的历史内容注入模型上下文。
- 每次请求开始时必须从云端状态重建模型可见上下文。
- 相同线程状态、相同请求输入、相同配置快照和相同 Skill 指纹应生成等价模型上下文。
- 上下文重建不得依赖上一次请求保留在进程内的 context manager。

### 7.4 配置解析

- 配置解析结果应可作为请求处理输入的一部分持久化或重建。
- 用户级配置、项目级配置、请求级覆盖必须有确定的优先级。
- 服务实例不得依赖启动时配置快照处理所有后续请求。

### 7.5 工具执行

- 工具调用必须绑定请求标识、turn 标识和工具调用标识。
- 工具执行结果必须可持久化。
- 长生命周期工具会话必须有租约和失效语义。
- 对无法恢复的工具会话，服务必须返回明确的中断或失败状态。

### 7.6 审批与权限

- 审批请求必须有可记录的标识和结构化载荷，但不要求成为跨实例可解析资源。
- 审批结果必须记录审批主体、审批范围、有效期和来源。
- “本次请求有效”和“当前会话有效”可在首个版本继续依赖运行实例内存；最终结果必须写入云端状态用于审计。
- 权限提升不得跨请求隐式复用，除非存在显式持久化授权策略。

### 7.7 输出与事件

- 事件必须包含请求标识、turn 标识、序号、类型、时间戳和载荷。
- 事件序号必须在请求内单调递增。
- 客户端必须能够按游标恢复读取。
- 面向人类的文本输出应由客户端渲染，服务输出以结构化事件为主。

### 7.8 兼容 CLI

- 现有 `codex exec` 类非交互调用应优先适配服务模式。
- 现有交互式命令可在迁移期保留本地执行路径。
- 本地 CLI 应支持指定服务地址、启动内嵌服务或使用默认本地服务。
- 机器可解析输出应保持稳定字段命名和错误语义。

### 7.9 云端状态存储

- 单次请求、turn、事件、审批结果、线程和配置快照必须写入云端持久化层。
- 现有 SQLite `state_db` 承载的线程元数据、goal、memory mode、backfill state 等运行时元数据必须迁移到云端数据库或云端状态服务。
- 写入路径必须支持幂等操作，避免请求重试产生重复业务记录。
- 状态读取必须支持按请求标识、turn 标识、线程标识、调用方标识和时间范围查询。
- 事件写入必须保持请求内顺序；跨请求不要求全局顺序。
- 云端状态模型必须显式记录 schema version，支持后续迁移。
- 本地实例缓存的状态必须可丢弃；缓存丢失不得影响已确认状态的正确性。
- 服务实例启动时不得要求扫描本地会话目录恢复全局请求索引。
- 云端状态必须支持任意实例按线程标识加载完整 resume 所需状态。
- 每次请求完成前，新增事件、线程元数据、配置快照引用、state_db 元数据和 Skill 指纹必须已写入云端。
- 无法确认云端持久化成功时，服务不得向调用方返回成功完成。

### 7.10 Skill 加载与本地缓存

Skill 定义的权威来源为集中式 NFS 目录。服务实例可将 Skill 文件复制到本地缓存以降低读取延迟和 NFS 压力，但本地缓存不得作为权威来源。

加载要求：

- 服务实例必须支持配置一个或多个 NFS Skill 根目录。
- Skill 加载必须记录来源路径、Skill 标识、版本指纹、加载时间和缓存路径。
- Skill 解析失败不得阻塞无关 Skill 加载；失败信息必须结构化暴露。
- 请求执行时必须记录实际使用的 Skill 版本指纹，保证结果可追溯。
- 当 NFS 暂时不可用时，服务可使用仍在有效期内的本地缓存；超出有效期后必须返回明确错误或降级状态。

本地缓存要求：

- 缓存键必须包含 Skill 来源路径和版本指纹。
- 缓存内容必须具备完整性校验，至少基于文件内容哈希或等价指纹。
- 缓存目录必须支持容量上限、过期清理和并发加载互斥。
- 缓存写入必须采用原子替换，避免并发读取到半写入内容。
- 不同租户或权限域的 Skill 缓存必须隔离，除非存在明确共享策略。

缓存失效要求：

- 必须支持基于版本指纹的强失效。NFS 中 Skill 内容变更后，新请求不得继续加载旧指纹，除非请求显式固定旧版本。
- 必须支持基于 TTL 的兜底失效，用于处理 NFS 元数据事件缺失或 watcher 中断。
- 应支持基于 NFS 文件元数据的快速检测，包括 mtime、size 和目录清单版本；最终一致性以内容哈希为准。
- 应支持主动刷新接口，用于部署系统在发布 Skill 后通知服务实例刷新缓存。
- 正在运行的请求应继续使用启动时绑定的 Skill 版本，避免同一请求内 Skill 定义变化。
- 新请求必须在加载阶段解析最新可见版本，并将版本指纹写入请求记录。
- 当检测到缓存指纹与 NFS 权威指纹不一致时，必须丢弃本地缓存并重新加载。
- 缓存失效和刷新失败必须记录指标与结构化日志。

## 8. 非功能需求

### 8.1 可扩展性

- 服务实例应支持无共享横向扩展。
- 同一线程的不同单次请求不得要求命中同一实例。
- 同一运行中请求可以绑定到 owner 实例；请求结束后的下一次请求必须允许命中任意实例。

### 8.2 可靠性

- 服务进程异常退出不得导致已持久化请求记录丢失。
- 请求最终状态必须可查询。
- 客户端重试不得导致重复执行已确认的幂等请求。
- 云端状态存储短暂不可用时，服务不得确认无法持久化的请求状态变更。
- NFS 短暂不可用时，服务只允许使用仍满足有效期和完整性校验的 Skill 缓存。
- 任意实例重启或下线后，后续新请求必须能由其他实例基于云端状态 resume。

### 8.3 安全

- 所有文件系统、网络、子进程和 MCP 操作必须继续受权限策略约束。
- 服务接口不得默认暴露到不可信网络。
- 调用方身份、授权范围和审计日志必须可关联。
- 敏感字段不得进入普通日志。

### 8.4 可观测性

- 必须提供结构化日志、指标和追踪标识。
- 每个线程、请求、turn、工具调用、模型请求应具备关联 ID。
- 错误应区分用户输入错误、权限错误、环境错误、模型错误和内部错误。
- 必须暴露云端状态存储读写延迟、错误率和重试次数。
- 必须暴露 Skill NFS 读取延迟、缓存命中率、缓存失效率、刷新失败次数和使用过期缓存次数。

### 8.5 性能

- 服务化不应显著增加单次非交互请求的启动开销。
- 事件持久化应支持批量写入或异步写入策略，但不得破坏事件顺序。
- 大输出必须分块传输和存储。
- Skill 本地缓存命中时，加载延迟不应依赖 NFS 实时读取。

## 9. 接口草案

接口命名仅用于需求表达，最终名称以 app-server API 设计为准。

### 9.1 `turn/run`

运行一次单次对话请求。该接口命名仅为需求草案，最终可映射到现有 `turn/start` 或新的 task API。

关键参数：

- `threadId`
- `createThread`
- `idempotencyKey`
- `input`
- `cwd`
- `settings`
- `permissionProfile`
- `approvalPolicy`
- `clientInfo`

关键响应：

- `requestId`
- `turnId`
- `threadId`
- `status`
- `eventCursor`

### 9.2 `turn/status/read`

读取单次请求状态。

关键参数：

- `requestId`
- `turnId`

关键响应：

- `request`
- `latestEventCursor`

### 9.3 `turn/events/list`

按游标读取单次请求事件。

关键参数：

- `requestId`
- `turnId`
- `cursor`
- `limit`

关键响应：

- `events`
- `nextCursor`

### 9.4 `turn/cancel`

## 10. 迁移策略

### 10.1 阶段一：服务边界显式化

- 梳理 CLI 当前命令中依赖进程内状态的路径。
- 定义线程、单次请求、事件、审批结果、配置快照的数据边界。
- 为非交互请求建立服务兼容路径。
- 定义请求进入时 load/resume、请求结束时 persist/release 的生命周期。

### 10.2 阶段二：云端线程状态与事件

- 引入云端线程、turn、事件表或等价持久化模型。
- 将流式输出转换为可恢复事件流。
- 将审批最终结果写入云端状态。
- 将本地会话状态迁移为云端线程、turn、事件和配置快照。
- 将 `state_db` SQLite 职责迁移为云端 DB 职责。

### 10.3 阶段三：CLI 客户端化

- 将本地 CLI 的非交互入口改为调用服务接口。
- 保留必要的本地兼容路径。
- 对输出格式建立兼容性测试。
- 将 CLI 对本地状态目录的直接依赖收敛到服务兼容层。

### 10.4 阶段四：多实例运行约束

- 移除同一线程后续请求必须命中同一实例的隐式依赖。
- 对运行中请求引入 owner 实例、租约和失败语义。
- 补充不同实例连续处理同一线程请求的集成测试。

### 10.5 阶段五：Skill NFS 与缓存改造

- 定义 NFS Skill 根目录结构、权限模型和版本指纹算法。
- 将 Skill 加载路径从本地固定目录改为 NFS 权威源加本地缓存。
- 实现 TTL、内容哈希、主动刷新三类缓存失效机制。
- 为 Skill 更新、NFS 不可用、缓存损坏、并发刷新补充测试。

### 10.6 阶段六：单次请求化

- 将现有长生命周期 thread 使用方式改为请求内加载、请求内运行、请求结束释放。
- `turn/run` 或等价 API 内部完成 resume，不要求调用方先显式 `thread/resume`。
- 保证第 N 次请求完成后，第 N+1 次请求命中任意实例时可恢复上下文。
- 保留运行中请求实例绑定，不做运行中跨实例接管。

## 11. 验收标准

- 服务进程重启后，已完成请求可查询完整状态和事件。
- 客户端断线后，可基于事件游标继续读取输出。
- 重复提交相同幂等键不会创建重复请求或重复 turn。
- 非交互 CLI 调用可通过服务路径完成，并返回与原路径等价的退出状态和结构化结果。
- 服务实例不依赖进程内会话映射处理已持久化请求的查询、事件读取和审批解析。
- 权限策略、沙箱策略和审计记录在服务路径下保持可验证。
- 单次请求、turn、事件、配置快照和 state_db 元数据写入云端持久化层，本地状态缓存删除后仍可查询已确认状态。
- 审批最终结果写入云端持久化层；审批处理本身不要求脱离原始运行实例。
- 同一线程第 N 次用户输入完成后，第 N+1 次用户输入命中任意其他节点时，可以基于线程标识恢复上下文并继续执行。
- 删除服务实例本地 `CodexThread`、进程内 context cache 和本地状态缓存后，下一次请求仍可通过云端状态恢复。
- Skill 从 NFS 权威源加载，本地缓存命中时可完成加载，缓存失效后新请求使用更新后的 Skill 指纹。
- Skill 更新期间，已运行请求继续使用启动时绑定的 Skill 指纹，新请求使用最新可见指纹。
- NFS 不可用且缓存未过期时，服务可按策略使用缓存；缓存过期或校验失败时返回结构化错误。

## 12. 风险与限制

- 长生命周期工具会话和 PTY 不要求跨实例迁移；实例失效时应进入明确的中断或失败状态。
- TUI 交互语义可能无法完整映射到无状态服务接口，需区分本地交互能力和服务能力。
- 事件持久化会增加写入路径复杂度，需要控制事件粒度和存储成本。
- 现有会话恢复逻辑可能包含进程内假设；单次请求模式要求每次 turn 前都能从云端状态重建上下文，迁移时需要通过集成测试覆盖。
- 权限审批仍可保留连接内交互；风险集中在审批最终结果的云端记录与审计一致性。
- 云端状态存储会引入网络延迟、部分失败和 schema 迁移问题，需要明确一致性模型。
- NFS 元数据缓存、时钟偏差和 watcher 事件丢失可能导致 Skill 更新感知延迟，需要 TTL 与内容哈希兜底。
- Skill 本地缓存若未按租户或权限域隔离，可能产生越权读取风险。
- Skill 更新与请求执行并发时，如果未绑定版本指纹，会导致同一请求内行为不可追溯。

## 13. 待决问题

- 服务协议应复用现有 app-server JSON-RPC，还是定义面向 CLI 自动化的新资源层。
- 单次请求接口应复用现有 `turn/start`，还是新增 `turn/run` 或 task API。
- 云端状态持久化应复用现有 thread/turn/item 模型，还是新增 request 作为 turn 外层记录。
- 本地 CLI 默认应启动内嵌服务，还是连接受管 daemon。
- 审批结果的“会话级有效”在保持实例绑定的前提下，应如何记录到云端状态以满足审计和恢复后的可解释性。
- 云端状态存储采用强一致数据库、事件日志，还是数据库加对象存储的组合。
- Skill 版本指纹采用目录级 Merkle 哈希、manifest version，还是文件内容哈希集合。
- NFS Skill 更新由部署系统主动通知，还是服务实例自行轮询；两者是否同时保留。
- 过期 Skill 缓存是否允许在只读任务中继续使用；如果允许，需要定义最大过期窗口。
